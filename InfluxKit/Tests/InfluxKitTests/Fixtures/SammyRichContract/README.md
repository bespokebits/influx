# Sammy rich feed contract files

These files are generated by the Sammy server's own tests, against the
origin `https://example.com` with made-up content, and copied here
byte for byte. `manifest.json` lists each one with its SHA-256 and the
contract version they belong to: version **8**, which added direct media
sources (`rich-feed-media-sources.json`: a batch request for four media IDs
and the answer, one each of direct image, direct video, use a grant and
gone; the thread form of the request; the limits and refusal; and the
upstream's side, which no reader sends) and changed no earlier file.
Version 7 added since reads
(`rich-feed-since.json`: a first page with its `sinceUrl`, the since read
that answers a late repost, a since read with nothing new, and the since
refusals) and changed no earlier file. Version 6 gave authors an
optional handle (`author.handle`) and posts an optional link card (`card`,
its picture a media ID): it changed `rich-feed-page-attribution.json` (another
author's handle, and a new last post with a card) and `rich-feed-thread.json`
(the handle and a card on its ancestors, and a `cardImageGrant`) by those
additions only. Version 5 gave authors an
optional picture (`author.avatar`, a media ID): it changed
`rich-feed-page-attribution.json` (a post's author, a reposter and a quote's
author with one) and `rich-feed-thread.json` (its ancestors' author, and an
`avatarGrant` beside `mediaGrant`) by those additions only. Version 4 added
the feed change stream (`rich-feed-events.json`, and `rich-feed-changes.json`
for the server's own upstream watcher, which no reader sends) and changed no
earlier file, as version 3 did when it added reposts, quotes and threads
(`rich-feed-page-attribution.json`, `rich-feed-thread.json` and
`rich-feed-thread-refusals.json`) and version 2 when it added media
(`rich-feed-page-media.json` and `rich-feed-media-grant.json`). They sit beside the article set in `../SammyContract`,
which they don't change.

- **Never edit them by hand.** `SammyRichContractTests` checks every hash
  against the manifest and that nothing else is in this folder, and the
  server's checks compare this manifest, at this path, with its own.
- **Replace them together**, all of them and the manifest, with the set the
  server generates for a new contract version, in the same change that
  updates the code that reads them.

What they cover: the rich feed list (with and without `account.id`), two
rich pages joined by `nextUrl`, an expired page, a 304 with the request
that earned it, the negotiation table with the headers of each 200, the
refusal bodies, the post identity cases, the legacy identity vectors, a
page whose post carries an image, a video and a GIF, a media grant
with its byte requests and refusals, a page with a repost, a quote with
media, an unavailable quote and a post with a thread, that thread with its
304 and grants for one of its posts' media and one of its authors' pictures, the thread route's
refusal bodies, and the change stream: its request, its frames, a whole
recorded stream with the events it carries, its limits and its refusals.

## What this build sends

- `GET /api/v1/feeds`: `Accept: application/vnd.sammy.rich-feed+json; version=1, application/feed+json`.
- A feed listed as posts: `Accept: application/vnd.sammy.rich-feed+json; version=1`.
- Any other feed, including one whose classification is unknown:
  `Accept: application/vnd.sammy.rich-feed+json; version=1, application/feed+json`.
- `If-None-Match` only with the `Accept` its `ETag` came back for.
- A media grant: `POST /api/v1/feeds/<feed>/media/<media id>/grant` with
  the account's token and no body, only to the account's own server. Its
  URL is taken only when it is https on that origin under
  `/api/v1/rich-media/`, and is read with no token, with
  `?variant=preview` for a preview and one `Range` when a player reads a
  video in pieces.
- A thread: `GET /api/v1/feeds/<feed>/threads/<ref>` with
  `Accept: application/vnd.sammy.rich-feed+json; version=1` and the
  account's token, only to the account's own server, with `If-None-Match`
  only for a thread it read before (its `ETag` starts
  `W/"rich-thread-v1-`).
- A thread post's media grant: as above, with `?thread=<ref>`.
- An author's picture, or a link card's: the same grant with the picture's
  media ID, and `?thread=<ref>` for a thread post's.
- The change stream, while the app is on screen and the account has a
  feed of posts: `GET /api/v1/feeds/events` with `Accept: text/event-stream`
  and the account's token, only to the account's own server, following no
  redirect; one per account (ADR 0038). On `ready` it reads each feed of
  posts, and on `feed.changed` that feed if it is one of the reader's
  sources, each as a normal conditional read.

## How the mapper is chosen

Only from the response, never from what the source says:

- `Content-Type` exactly `application/vnd.sammy.rich-feed+json; version=1`
  and a body whose `format` and `version` are the rich page's (or list's):
  rich.
- `Content-Type` `application/feed+json` or `application/json` (parameters
  ignored) and a body with no `format`: article.
- Anything else, a missing `Content-Type`, a feed listed as posts answered
  as an article, or one listed as articles answered rich: refused as a bad
  response. A 406 is "unsupported". Nothing falls back to articles.
- A 304 counts only when its `ETag` is of the stored format: a rich one
  starts `W/"rich-v1-`, a thread's `W/"rich-thread-v1-`.
- A thread counts only with the rich `Content-Type` and a body of format
  `sammy.rich-thread`, version 1, for the reference and the post asked
  about; one that breaks any rule is refused whole.

## What is stored and what is ignored

Each rich post is stored as a post with no title or actions: its
`id` (the row, per feed), its full `text` exactly as sent, its links (placed
where their URL or text is in the text, else listed after it), its author's
name, its original URL, its `publishedAt` and its media. Each attachment is
stored at its own size with its kind, alt text and duration, and a
`sammy-media:` reference in place of a URL (never a grant's URL, which
expires); a post whose media breaks the contract is dropped, and an
attachment of an unknown kind is left out. Its merge key is
`sammy-post:<server>:<canonicalId>`, so the same post in two feeds of one
account is one row and two posts that share a URL are two. The list's
classification of each feed is stored with its source and synced.

An author's picture is stored as the post's author picture, and a
reposter's as its booster's, each a `sammy-media:` reference drawn like any
other profile picture; one that isn't an object with a media ID is left out
and the post stays. A quote's author's picture is read but not shown: a
quote card has no picture of its author. A row joined with a copy from
another service shows the rich copy's picture, else the other copy's.

An author's handle is the row's handle, and a quote's author's the quote
card's; without one, the row shows the host of the author's URL. A post's
link card is the row's link card, its picture a `sammy-media:` reference at
the card's size, and its link is not listed again after the text; it is kept
only on a post with no media and no quote. A handle or a card that breaks the
contract is left out and the post stays.

Who reposted a post is stored as its booster, so the row says "Boosted by"
as for any other service; a quoted post is the row's quote card, its first
picture a `sammy-media:` reference; an unavailable quote has no card. A
post's thread reference is kept with it (`actionRef`, `thread:<ref>`), and
only a post that has one offers its thread. Thread posts are never stored:
the thread is read when it is opened, kept in memory with its `ETag`, and
its posts' media references name the thread (`?thread=<ref>`). Its gaps
are read but not shown yet.

Each post's `{canonicalId} ∪ aliases` is stored with it and joins it with
other copies of the same post: rich posts of the same server that share an
identity, and native Mastodon or Bluesky posts whose legacy identity it
lists (ADR 0014). `RichPostIdentityTests` computes every legacy identity
vector byte for byte and joins the stored identity case through the store.

Ignored: `capabilities`, `extensions`, the page's `source` and
`retentionDays` (posts are kept 7 days whatever it says). ADR 0031 says why.
